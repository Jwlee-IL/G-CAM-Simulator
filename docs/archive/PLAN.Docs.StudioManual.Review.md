## 2. Process gaps and deliberate adaptations

The author's document-automation procedure from another project was read as a process source only. Its current revision has more requirements than the plan summary. The following are restated as principles for GCAM; no external schema names, templates, product content, or case data are adopted.

| Missing / incomplete principle | Concrete GCAM treatment |
|---|---|
| Manual and verification are two views of the same execution | Write a narrative chapter record and a paired verification-procedure record with one execution ID and one append-only log. Each product check belongs to a stable verification step. Cross-check identical case sets and check-line membership; a manual pass requires a verification pass. Do this even without generating a separate verification report. |
| Reference chapters also require checks | Enumerating a settings page requires checking that the listed fields are present, visible, named and in the expected editable/locked state. A screenshot or successful navigation alone is not sufficient. |
| Identity is more than the executable | Hash the fixed deployed application/dependency/configuration manifest before and after execution, plus runner, registry, verification catalog, risk and static sources. Subject and runner identity are separate. Runtime assets can alter the result without changing the apphost executable. |
| Immutable source snapshots and source status | Retain exact source revisions/hashes, including each static chapter and the verification catalog. The author records source review separately; the generator cannot manufacture it. A draft can be assembled for review, but completeness/provenance must be explicit. |
| Failure, absence and partial execution are distinct | An unmet expectation after its stimulus is failed; a step never reached or a failed setup is not executed. Capture rejection is missing evidence, not a product failure. Preserve incomplete/aborted execution and all results; never copy the chapter verdict onto every step. |
| Selection is whole-case replacement | Among compatible original executions choose the latest started execution with an attempted step; if all are unexecuted choose the latest recorded case. Later failures supersede passes. Do not combine steps from different runs. Retain unchosen candidates and their selection reasons. |
| Integrity failures differ from omissions | A declared file missing, hash mismatch, unknown schema, inconsistent sibling record or mixed subject/procedure stops generation. An absent optional registered source or never-run chapter produces a notice. A rejected planned capture produces a notice at that step. Missing source bytes that were claimed and hashed are corruption, not a soft omission. |
| Risk mapping is bidirectional | Risk register names chapters; run blocks name notice IDs and placement steps. Check both directions and static notice wording. Unknown notice IDs produce a missing-source notice; notices placed in a forbidden chapter stop generation. Missing required placements create missing-notice entries; never invent a placement. |
| Individual chapters need lineage too | Each generated chapter has its run/case/step and output hash entry; assembled Markdown alone is not a sufficient archive. Use stable chapter cross-reference tokens and explicitly identify a reference to an omitted chapter. |
| Marks and captions cannot invent screen wording | Record visible text and target rectangles together. Accessible names of icon-only controls are not visible labels. Under strict adoption, leave those icons unmarked, describe their accessible/tooltip text only after recording it, or open and capture the tooltip. Do not silently equate UIA Name with screen ink. |
| Derived figures are restricted | Preserve original PNGs. A crop and a marked overlay are separate derivatives from the original; do not crop an overlay. Record original, mark-file, operation and result hashes. Validate consecutive mark numbers, integer bounds, positive size and capture association. |
| Capture and assembled-document quality differ | Reject unusable captures mechanically before saving, then inspect the final rendered Markdown and every figure in turn 3. File existence/size does not prove readability. Record intentional removal of a mark and the reason; rerender outputs and retain the new generation record. |

Do **not** adopt patient/device/operator workflows, account-name tables, organisation forms, signatures, document-control IDs, a regulated instrument release claim, or a second locale. Do not transplant the source's temporary-index/git-tree procedure: use TODO-28's canonical source-file manifest/hash without git mutations. Its pixel text-overlap measurement is not supplied by Python's standard library; adopt measured UIA text bounds plus a conservative placement check rather than claiming OCR. Keep final human figure review separate from automatic product verdicts. Any departure from the process is recorded as a GCAM decision, not disguised as exact compliance.

### 2.1 Supplementary process reconciliation

**Revised after UI v3.0.1 — gates and profiles.** This review is P0: shortened G0, no runtime G1–G6 claims. The future manual result bundle is P4 and requires full G0–G6. A shared regression bundle would be P2 with its own G2–G6 and review status; no P3/regulated-evidence claim is needed merely because paired automatic verification records exist. Record common G0/G1 once at execution level using the strictest included profile. Keep bundle gates separate. Gate status is passed, blocked or not applicable; shortened passage is permitted only where that profile permits it, with omissions recorded. A profile-required gate cannot be waived by an implementer's judgment. This replaces the first review's unnamed “manual evidence profile” recommendation: profiles identify result use, not harness maturity.

**Revised after UI v3.0.1 — existing-harness adoption.** Declare adoption of the existing harness, not a new harness merely because the manual adds scenarios. Establish the entire harness's safety floor first, including survey destinations, failure diagnostics and launch/cleanup helpers. Then qualify only the changed/shared driver, selector, verdict and manual scenario scopes needed for P4; each scenario belongs to one scope and cannot be better qualified than its dependencies. Old passes remain historical; they are reusable gate evidence only when build/script/input/environment and current negative controls can be verified. Unchanged scopes can remain diagnostic-only in a transition list with permitted use, residual risk, responsible role, qualification condition and expiry. Do not rewrite all historical manifests. This avoids the earlier implication that new manual code alone could bypass legacy launch and safety gaps.

**Revised after UI v3.0.1 — safeguards and human acts.** First use a current mechanical check or observation; if unavailable, add a harness-owned fixture, instrumentation or checker; only then use an act in the closed list below. The author sets purpose, authority and accepted residual scope, but does not operate Studio to establish a gate. The planner/automation runner drives the observed run and scenarios. The current request approves reading and review only: no row below grants desktop permission. These are GCAM process labels, not imported product/template identifiers. A source-act reference is a crosswalk to the two procedures' closed lists, not an approval record.

The lists intentionally omit the unused source-act slots; the crosswalk invents no additional category. All newly recommended author acts above are **revised after UI v3.0.1** because the two matching closed lists narrow who decides what. Keep raw author-statement provenance in a controlled local approval source; public copies use role IDs and clean-room-safe targets, with a hash/lineage claim. Never write identifying quotes into this review, invent statements, or treat this supplementary read request as approval of the future charter. The author can bundle charter, policy, scope and source decisions, but permission expansion remains tied to the reviewed change it covers.

**Revised after UI v3.0.1 — safety and one observed-run mechanism.** Source availability and source-to-binary traceability are separate assertions. Current env redirection and “no writes in sandbox” do not establish all-path isolation. Re-survey the reachable current deployment, list each product and harness effect with declared/default and resolved destination, establish technical prevention first, then instrument an automation-driven launch/flow/close. Record file/process/network and any applicable registry channels, attribution rules, positive controls, excluded locations/filters and blind spots. Use a disposable approved session if unresolved effects cannot be technically contained; do not suggest that a known-folder source scan substitutes for a missing technical boundary.

The trigger chooses the flow, not a separate human audit: initial G1 qualification is launch–idle–exit without tree dump or automatic control input; a permission/isolation expansion uses one approved pilot after the concrete commit and AUTH-ALLOW decision; a product-build-only change starts with the G3 pilot; a new screen/flow using already allowed actions is first run under observation. Adding only prohibitions does not require permission expansion. Changed/new IDs begin prohibited until their action is classified and concretely allowed. Before any observed control flow, compare selector usage against product ID declarations in both directions. None of these runtime operations was attempted in this turn.

**Revised after UI v3.0.1 — promotion and requalification.** Validate a promised effect on every active observation channel. Missing positive control means the instrument is unproven, not “no effects”. First-qualification G1 is blocked during observation; on later reopenings its previous passing basis remains recorded with the reopening reason unless an actual stop condition blocks it. Results remain blocked until the same run supplies a valid G1 basis. If channels pass and no undeclared effect or unresolved candidate remains, finalise the observed run as the new basis and promote its *own* scenario results into the appropriate G2–G6 evidence; no compulsory second execution solely for promotion. A P1 diagnostic run cannot otherwise be renamed P4 retrospectively. Binding the basis requires matching product deployment, isolation-content fingerprint, path rules and registered images; a changed build triggers the observed pilot instead of declaring every scope permanently unqualified.

An undeclared product effect ends the run unsafe and blocks G1. Keep the prior manifests immutable; an append-only qualification/invalidation record withdraws affected result uses identified through semantic actions and touched controls, or conservatively since the last basis when attribution is insufficient. An unresolved candidate requires better instrumentation/rerun before AUTH-CLASSIFY. Separate effects directly attributable to the app or its requested service from unrelated runtime bookkeeping/background activity; code rules do the classification. For unaffected later evidence runs, recommend a narrower watch on uncovered destinations, with forwarded ambiguous candidates and blind spots; it is not a substitute G1 audit and cannot establish a new safety basis. These distinctions replace the first review's blanket rerun/cleanup simplification.
